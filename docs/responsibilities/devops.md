# 研发运维岗职责标准

## 文档版本


| 版本号 | 修订时间   | 修订者 | 备注 |
| ------ | ---------- | ------ |----|

## 一、责任范围

> **岗位定位**：以服务器和系统运维为主要职责，同时承担分配的需求、优化和 BUG 任务。运维范围可以覆盖当前项目及其他分配项目，研发任务范围按实际分工确定。

文中专业术语的通俗解释及例子见[专业术语说明](/responsibilities/devops-glossary)。

| 工作范围 | 负责内容 | 责任要求 |
| -------- | -------- | -------- |
| 项目运维 | 分配项目的服务器、网络、中间件、数据库、应用服务和数据备份 | 明确维护范围、主责人员和备岗人员，持续跟踪运行问题 |
| 运维能力建设 | 自动化构建部署、监控告警、日志查询、备份恢复和运维脚本 | 负责搭建、接入、验证、文档交付及持续维护 |
| 跨项目支持 | 其他指定项目的发布、服务器维护和故障处理 | 按分配的项目与资产清单执行，明确与原项目负责人的交接关系 |
| 项目研发 | 分配给本人的需求开发、功能优化和 BUG 修复 | 承担编码、自测、文档和交付责任，执行与研发岗相同的开发标准 |

跨项目运维按分配范围承担服务器与服务维护责任；业务代码问题按模块和任务归属确定修复人员。

云资源、虚拟化、容器、物理硬件和机房设施按项目实际使用情况明确维护范围；涉及供应商或其他维护团队的资源，必须记录责任边界和联系渠道。

## 二、主要工作职责

### 2.1 服务器、网络与运行环境

- 负责 Linux、Windows 服务器初始化、运行环境安装、服务注册、开机启动、系统补丁和资源调整。
- 维护域名解析、HTTPS 证书、端口、防火墙、反向代理和远程接入配置，处理连通性及访问异常。
- 建立环境配置和资产台账，记录服务器用途、所属项目、部署服务、依赖关系、维护人、资源配置和到期时间。
- 执行巡检、日志归档和容量检查，建立资源使用与服务性能基线，跟踪磁盘、内存、带宽及存储增长。
- 配合研发开展压测和性能排查，提交扩容或配置优化方案，实施后验证效果；定期识别闲置资源、异常费用及可复用资源。
- 负责资源开通、扩容、迁移和下线的技术评估、实施及验证。
- 迁移或下线前必须核对关联服务和数据保留要求，完成必要的归档、迁移与验证，再释放资源、清理接入配置和回收权限，更新台账。

### 2.2 中间件、数据库与数据保障

- 负责数据库、缓存、注册中心、文件存储等服务的部署、配置、运行维护和升级验证。
- 排查连接异常、服务不可用、空间不足和性能问题；涉及业务查询、索引或代码调整时，协调对应研发人员处理。
- 建立数据库、文件和关键配置的备份任务，明确备份周期、保留期限和存放位置，检查任务结果并验证恢复能力。
- 数据库结构和业务数据变更由实际研发人员编写并验证 SQL，提供脚本、影响说明及执行顺序，对 SQL 准确性、执行顺序及应用与数据库变更的兼容性负责。
- 研发运维负责核对目标环境和数据库，按交付脚本及顺序执行并记录结果；选错环境、漏执行、重复执行或未按交付顺序执行等操作错误由实际执行人负责。执行失败时，必须停止后续相关操作并通知研发处理。
- 应用回滚与数据库恢复必须分别评估；涉及数据恢复时，必须确认允许丢失的数据范围和恢复影响，不得直接以旧备份覆盖生产数据。

### 2.3 自动化构建与部署建设

研发运维岗必须负责建设并维护发布流水线，使构建、部署、验证和回滚能够按统一规则执行。

| 建设内容 | 必须完成的工作 | 完成依据 |
| -------- | -------------- | -------- |
| 构建环境 | 配置构建执行节点、JDK、Node.js、包管理器和依赖源，固定必要版本 | 指定提交能够在构建节点成功打包 |
| 发布流水线 | 接入代码仓库，配置测试、灰度、生产各环境的触发条件与执行步骤 | 各环境均有可用的构建部署入口及执行日志 |
| 部署脚本 | 实现上传、备份旧版本、替换、启动、健康检查和失败处理 | 部署失败能够停止后续操作并反馈失败结果 |
| 产物管理 | 保存版本、提交号、构建编号、产物校验值和存放地址，设置保留规则 | 能够确定当前线上包及历史可回滚包的来源 |
| 环境与权限 | 分离环境配置和凭据，限制灰度、生产部署权限，防止同一环境并发发布 | 测试任务无法误部署生产，凭据不进入源码和构建日志 |
| 回滚与维护 | 建设回滚入口，验证旧版本恢复，维护流水线和脚本本身 | 在约定环境完成部署、失败告警和回滚验证，并交付使用说明 |

- 流水线、脚本和配置模板必须纳入版本管理；研发负责提供并维护业务构建脚本、工具版本、构建参数、启动参数和健康检查方式，研发运维负责统一构建环境、流水线及部署脚本的集成与维护。
- 自动化尚未覆盖的项目，测试包由研发构建并交付，灰度、生产包由研发运维统筹构建和核验，各环境部署由研发运维按发布清单执行；同时将补齐自动化列入工作计划。
- 构建失败涉及代码、依赖声明、业务构建脚本或业务测试时，由对应研发人员修复；涉及构建环境、凭据、网络或部署脚本时，由研发运维处理。

### 2.4 服务器监控、告警与日志建设

研发运维岗必须完成监控系统搭建、项目接入、告警配置和持续维护，监控范围必须覆盖实际维护的服务器与服务。

| 监控范围 | 主要检查内容 | 处理要求 |
| -------- | ------------ | -------- |
| 服务器与网络 | CPU、内存、磁盘空间、磁盘 I/O、网络流量、主机存活和关键端口 | 识别资源不足及连通性异常，结合容量趋势处理 |
| 应用服务 | 进程状态、接口可用性、响应时间、请求量、错误率和关键日志 | 告警能够关联项目、服务和排查入口 |
| 数据库与中间件 | 连接数、可用性、存储使用、慢查询及项目涉及的复制或集群状态 | 区分基础服务异常与业务性能问题，落实处理人员 |
| 发布与定时任务 | 构建部署结果、健康检查、定时任务和备份执行结果 | 任务失败必须可发现，不能只依赖人工查看日志 |
| 域名与证书 | 到期时间、证书有效性和 HTTPS 可用性 | 提前提醒并跟踪续费、更新和验证结果 |
| 监控平台自身 | 采集状态、数据更新时间、通知通道和平台资源 | 采集中断和通知失败必须能够发现和处理 |

- 每项告警必须明确阈值或触发条件、持续时间、通知对象、处理人和升级规则，并通过模拟异常验证通知能够送达。
- 研发负责提供业务健康检查接口、必要指标和可定位问题的日志；研发运维负责采集、看板、通知和告警处理流程。
- 日志必须明确存放位置、保留期限、访问权限和查询方式；对重复、无效告警应持续调整，避免影响故障识别。

### 2.5 故障响应与运行维护

1. 按约定时限接收告警或故障反馈，确认受影响项目、服务和业务范围，记录响应时间。
2. 优先恢复服务，按预案执行重启、切换、扩容或回滚等措施；无法独立解决或达到升级条件时，按项目故障升级规则联系对应责任人，落实并记录接手人员。
3. 环境、网络和中间件问题由研发运维处理；业务代码问题由对应模块负责人修复，研发运维持续跟踪恢复和发布。
4. 涉及云平台、运营商、机房或第三方服务时，负责技术报障、提供排查证据并跟踪恢复，向项目负责人同步影响和进展；客户侧业务通知由项目负责人组织。
5. 恢复后验证服务状态及核心功能，记录恢复时间、原因和遗留问题；重复故障和重大故障必须落实改进任务并跟踪完成。

### 2.6 安全、账号与凭据管理

- 按授权开通、调整和回收账号权限，定期复核服务器、数据库和运维平台的访问范围，及时处理离职、调岗及支持任务结束后的权限回收。
- 统一管理密码、密钥和访问令牌的存放、使用与轮换，明确保管人和使用范围；凭据不得明文进入源码、普通文档或日志，泄露后必须按预案更换并排查影响。
- 维护系统和服务的安全配置，关闭无用服务和访问入口，排查漏洞与版本风险，按风险安排补丁或升级，并完成变更前测试和整改后验证。
- 检查异常登录、越权访问和关键操作记录，按项目要求保留审计日志；发现安全事件时，按应急流程处理并联系相关责任人。

### 2.7 配置与非发布类变更管理

- 维护各环境的配置基线，明确服务版本、端口、网络规则、启动参数和环境差异，定期核对实际配置，处理未记录的变更。
- 域名解析、防火墙、数据库参数和服务器配置等变更必须纳入项目变更流程，执行前明确影响范围、执行人、时间、验证方式和回退措施；涉及共享资源时先完成协调。
- 变更完成后必须验证服务状态并更新配置记录；紧急变更按预案执行，处理后补齐执行过程、结果和配置更新记录。

### 2.8 整体恢复与容灾保障

- 与项目负责人明确系统重要程度、允许丢失的数据范围和恢复时间目标，制定与资源条件匹配的恢复方案。
- 形成服务器损坏或环境不可用后的恢复步骤，覆盖资源重建、网络接入、账号与凭据、基础服务、应用和数据恢复，明确依赖关系及执行顺序。
- 对已配置主备或集群的项目，维护故障切换与回切方案；采用重建恢复的项目，必须验证环境和服务能够按文档重建。
- 按项目约定周期及重大变更后的安排开展恢复演练，验证整体服务和核心业务能否在目标内恢复，记录差距并跟踪整改。

### 2.9 运维平台自身维护

- 按分配范围维护代码仓库、CI/CD 平台、构建节点、制品库、监控和备份平台，明确各平台的主责及备岗人员。
- 负责平台服务状态、版本更新、容量、权限和证书维护，按保留规则清理执行日志、缓存及过期产物，保留必要的回滚版本和记录。
- 备份平台配置及必要数据，维护迁移和恢复步骤；平台升级或故障恢复后，验证构建、部署、产物访问、监控通知和备份任务等相关功能。

### 2.10 研发任务交付

- 按分配任务完成需求、优化和 BUG 工作，不得因兼任运维而省略评审、自测、接口文档和交付要求。
- 承担研发任务时，必须维护对应构建脚本、工具版本和参数说明，并按第 3.2 节交付测试包或构建所需信息。
- 涉及部署方式、端口、配置、数据库或基础资源变化时，必须同步更新部署说明。
- 运维故障或发布任务影响研发排期时，必须同步项目负责人，由其协调任务优先级和交付时间。

## 三、研发完成后的发布分工

以下为本标准的默认分工。每个项目必须明确各角色对应人员；测试、灰度和生产分支名称以项目实际配置为准。

### 3.1 角色责任

| 角色 | 负责事项                                         |
| ---- |----------------------------------------------|
| 研发人员 | 负责代码及 SQL 准确性、自测、发布内容确认，以及测试、灰度、生产分支的合并和冲突处理；维护构建脚本、工具版本及参数说明，无流水线时交付测试包和构建记录，提供发布说明并修复问题 |
| 产品或测试人员 | 执行功能测试、回归、灰度验证和上线后业务验证，给出验收结论及遗留风险           |
| 研发运维人员 | 统一维护构建环境和流水线，固定生产发布提交或标签，统筹灰度、生产包的构建与接收核验，负责各环境部署、产物管理、环境配置、技术检查、监控观察和回滚执行 |
| 项目负责人 | 确认灰度、生产发布时间和上线安排，依据验收结论批准发布，协调故障和排期冲突 |


研发运维人员承担业务研发任务时，同时履行对应研发人员的职责。分支合并、SQL 交付、发布版本固定、上线确认和部署执行必须按实际分工记录责任人及结果；人员兼岗时，仍须分别履行对应职责。

### 3.2 各环境由谁合并、打包和部署

测试环境由研发完成自测后合入测试分支，按构建方式交付测试包或构建所需信息；灰度、生产环境按以下分工确认发布。

研发合并后必须确认合并结果与本次发布任务一致；冲突处理改变代码时，研发必须重新自测，产品或测试在对应环境验证受影响内容。

| 环境 | 代码合并与部署条件 | 验证与放行 |
| ---- | ------------------ | ---------- |
| 测试环境 | 研发完成自测后合入测试分支，即可执行测试部署 | 产品或测试执行功能测试和回归，研发修复问题 |
| 灰度环境 | 测试通过后，研发按本次发布任务将变更合入灰度分支，项目负责人确认发布安排 | 产品或测试验证业务，研发运维检查日志、接口和资源情况，记录灰度结果 |
| 生产环境 | 灰度通过且获准发布后，研发合入生产分支，研发运维固定本次生产发布提交或标签 | 研发运维完成技术检查，产品或测试验证核心业务，项目负责人确认发布完成 |

构建与部署按目标环境是否已接入自动化流水线分别执行：

| 环境 | 已部署自动化流水线 | 未部署自动化流水线 |
| ---- | ------------------ | ------------------ |
| 测试环境 | 合并后流水线自动打包部署；研发运维负责流水线配置和维护，异常按第 2.3 节分工处理 | 研发从测试分支确定的提交执行构建脚本，交付测试包和构建记录，研发运维核验后部署 |
| 灰度环境 | 发布安排确认后，研发运维触发流水线生成灰度包并部署 | 发布安排确认后，研发运维从灰度分支确定的提交，在统一构建环境中手动打包，核验后部署并记录结果 |
| 生产环境 | 研发运维基于固定生产提交或发布标签触发流水线，核验正式包后按发布窗口部署 | 研发运维从生产分支的固定提交或发布标签，在统一构建环境中手动构建正式包，核验后按发布窗口部署 |

**无流水线时，测试包由研发打包，灰度、生产包由研发运维统筹构建、核验和部署；所有方式均必须保留构建、产物和部署记录，并执行相应验证及回滚要求。**

研发已在统一构建环境生成灰度或生产候选包时，研发运维必须核验代码来源、构建记录、产物校验值及对应验证结果。符合目标发布版本和环境要求的，可以直接接收并部署，无需因打包人员不同而重新打包；产物发生变化时必须重新完成相应验证。

需求和优化任务必须满足[需求流程](/workflow/)或[优化流程](/workflow/optimization)中的测试及客户上线前测试要求；BUG 任务按[BUG 处理流程](/workflow/bug)执行。相应确认结果必须纳入发布依据，紧急发布按第 3.4 节执行。

### 3.3 正式包与上线交接要求

1. **研发交付。** 研发必须提供任务清单、自测结果、部署模块、构建脚本、工具版本及参数说明、配置变化、数据库脚本及验证结果、执行顺序、外部依赖和回滚注意事项。信息不完整时，由研发补齐后再发布。
2. **构建核验。** 研发运维在研发完成生产分支合并后，固定本次发布提交或创建发布标签。正式包必须在统一构建环境中基于该提交或标签生成，关联版本、提交号、构建记录和产物校验值，由研发运维核验。使用流水线时保留流水线执行记录；手动构建时记录构建环境、命令和执行人。不得使用研发本机临时打包结果直接上线。固定后新增改动时，研发必须说明变化并确认受影响的验证范围，研发运维重新固定发布版本；不得移动已用于发布的标签或覆盖已登记产物。
3. **产物验证。** 正式包上线前，研发负责差异说明及必要自测，产品或测试负责受影响业务验证，研发运维负责构建来源、产物校验值和目标环境适配检查。业务验证在测试或灰度环境进行；支持跨环境复用的产物应复用已验证版本，因环境参数需要分别构建的，必须记录构建配置差异及验证结果。产物变化时必须重新验证受影响内容，并将验证结论关联到实际发布包。
4. **部署准备。** 研发运维必须确认目标服务器、备份、配置和旧版本，并与产品或测试明确验证安排、观察时段、关键指标及回滚触发条件。执行 SQL 前必须核对目标数据库、脚本版本及历史执行记录，按研发交付顺序执行并留存结果；执行异常按第 2.2 节处理。
5. **执行与观察。** 研发运维按发布窗口执行部署，检查启动、健康接口、日志和资源状态；产品或测试验证核心业务。技术检查、核心业务验证及约定观察均通过后，由项目负责人确认发布完成，记录实际版本、服务器、时间、执行人和验证结果。
6. **异常处理。** 出现发布失败或达到预先确认的回滚条件时，研发运维按预案停止或回滚并通知项目负责人。涉及数据恢复或未预定的高影响措施时，必须先确认影响和执行方案。

### 3.4 紧急修复与发布

- 生产故障、严重安全风险等需要立即恢复服务时，允许按项目应急预案执行紧急发布。项目负责人或预案指定的授权负责人必须确认发布安排、验证范围，以及需调整或事后补齐的流程事项，并记录原因和风险。
- 研发负责紧急修复、自测及分支合并，产品或测试负责关键业务验证，研发运维负责固定提交或标签、构建核验、部署及观察。紧急发布必须保留版本追溯、必要验证和回滚措施；其余要求按第 3.2、3.3 节执行。
- 无法联系确认人员时，研发运维只能执行应急预案已授权的恢复操作，并按升级规则继续联系对应责任人。
- 恢复后，研发必须将紧急修复同步至相关研发、测试、灰度和生产分支，避免后续发布覆盖修复；产品或测试完成需补齐的验证，研发运维补齐发布记录，项目负责人组织复盘，并明确遗留任务的责任人和完成时间。

## 四、跨项目协作与权限

- **维护分工**：按项目和资产清单分配主责及备岗；接管其他项目时，必须移交并核验服务器、服务、配置、部署方式、监控、备份和待处理问题，明确遗留问题的责任人及处理安排。
- **共享资源**：同一服务器、网络或中间件涉及多个项目时，必须明确统一维护人；项目运维主责负责协调和跟踪，变更由指定维护人执行，并通知受影响项目。
- **任务安排**：生产故障和影响业务的紧急风险优先处理；常规发布、巡检、能力建设和研发任务统一纳入排期。多个项目冲突时，由相关项目负责人协调，必要时提交部门负责人确定顺序。
- **服务时间**：必须明确日常保障时段、非工作时间的响应安排、故障响应与升级时限及联系人，并安排备岗，避免依赖单人长期在线。
- **运行目标**：与项目负责人明确服务可用性、关键接口性能、故障恢复及备份恢复目标，按业务影响确定保障要求和改进优先级。
- **定期复核**：按项目约定周期汇总故障、发布、备份、告警、容量和资源费用情况，对照运行目标识别差距，形成有责任人和完成时间的改进任务。
- **操作授权**：按维护范围分配服务器、流水线和部署权限；临时支持结束或权限到期后必须回收。流水线变更、手工生产操作和紧急发布必须可追溯。

## 五、工作产出与验收

| 交付内容 | 必须包含的信息 | 验收依据 |
| -------- | -------------- | -------- |
| 运维清单与计划 | 项目与资产归属、依赖关系、维护人、运行目标、巡检安排、服务时段和故障升级规则 | 维护范围和责任明确，接管、迁移及下线信息与实际一致 |
| 自动化部署能力 | 构建环境、流水线、部署脚本、使用说明和回滚入口 | 能从指定提交完成构建部署，并验证失败通知及回滚 |
| 监控告警能力 | 监控对象、指标、阈值、通知对象、处理人和看板入口 | 维护范围内的关键对象已接入，异常能够通知到对应人员 |
| 备份与整体恢复能力 | 备份范围、周期、保留期限、恢复目标、环境重建步骤、恢复顺序及演练结果 | 备份可用，整体服务和核心业务恢复符合项目约定 |
| 安全与权限管理 | 账号权限清单、凭据管理规则、漏洞整改和审计记录 | 权限与维护范围一致，失效权限已回收，安全问题已验证处理结果 |
| 配置与变更管理 | 环境配置基线、配置差异、变更影响、验证和回退记录 | 实际配置与记录一致，非发布类变更可追溯 |
| 运维平台维护 | 平台清单、维护分工、版本、备份、保留规则和恢复步骤 | 平台可用，相关构建、部署、通知和备份功能通过验证 |
| 发布与故障记录 | 版本、产物、执行过程、影响范围、验证结果、外部报障及改进任务 | 发布可追溯、故障可复盘、遗留问题有责任人 |
| 运行复核与资源优化 | 运行指标、容量趋势、资源费用、优化方案和处理结果 | 目标差距有改进安排，资源调整效果可核验 |
| 研发交付与运维文档 | 代码、自测结果、部署说明、配置清单、操作规程和交接信息 | 按研发任务验收，备岗人员能够按文档执行维护 |

工作记录必须关联项目任务或运维工单；流水线、监控和备份平台已有的日志可以直接关联，不得为同一事项重复建立无必要的记录。
