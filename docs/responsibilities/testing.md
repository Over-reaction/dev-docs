# 测试岗职责标准

## 文档版本

| 版本号 | 修订时间   | 修订者 | 备注               |
| ------ | ---------- | ------ | ------------------ |
| V1.0.0 | 2026/11/12 |        | 按岗位职责标准细化 |

## 一、责任范围

> **岗位定位**：独立承担分配项目或模块的测试工作，覆盖需求、优化和 BUG 任务，负责需求分析、测试设计、测试执行、缺陷复测和发布业务验证，输出与实际版本对应的测试结论，并持续建设接口测试和基础自动化能力。

| 工作范围     | 负责内容                                               | 责任要求                                                       |
| ------------ | ------------------------------------------------------ | -------------------------------------------------------------- |
| 项目测试     | 分配项目或模块的功能、接口、数据、权限和关联业务验证   | 明确测试范围、验收依据、版本和责任人，保留执行及问题记录       |
| 发布验证     | 测试、灰度环境验证，客户上线前测试支持及生产业务验证   | 测试结论关联实际发布版本，明确已验证内容、未验证内容和遗留风险 |
| 测试能力建设 | 用例库、接口调试与测试用例、自动化脚本、测试数据和报告 | 负责建设、使用说明、执行验证及持续维护                         |
| 跨项目支持   | 其他指定项目的测试、缺陷复测和上线支持                 | 按任务分工接收需求、环境、用例及问题信息，明确排期和交接人员   |

每个项目必须明确测试主责、备岗及协作人员；共享功能和跨模块任务必须明确统一跟踪人员及各方验证范围。

## 二、主要工作职责

### 2.1 需求理解与评审

- 依据需求文档、原型、业务流程、接口文档及已确认的业务规则，梳理测试范围和验收标准，关联对应需求、优化或 BUG 任务。
- 参与需求和技术方案评审，识别业务规则遗漏、边界不清、异常流程缺失、权限及数据隔离问题，记录疑问并跟踪确认结果。
- 业务规则和预期结果存在争议时，由产品人员组织确认，测试按确认结果更新用例；不得以个人理解替代已确认的业务规则。
- 需求变更时评估对用例、测试数据、回归范围和排期的影响，及时同步产品、研发及项目负责人。

### 2.2 测试方案与排期

- 根据任务范围和业务影响制定测试计划，明确测试对象、重点场景、执行方式、环境、数据、人员、时间和完成条件。
- 识别跨模块、第三方接口、定时任务、账号权限及设备等依赖，明确提供人员和就绪时间；无法满足测试条件时必须记录影响并同步处理。
- 根据发布批次安排功能测试、缺陷复测、回归和上线支持，预留修复后的验证时间；核心流程、公共能力和高风险变更必须纳入测试范围。
- 提测延期、环境故障、需求变化或紧急任务影响测试排期时，必须同步项目负责人，由其协调优先级和交付时间；同步更新测试范围及风险。

### 2.3 测试用例设计与维护

测试用例必须记录关联任务、前置条件、账号或角色、测试数据、操作步骤和明确的预期结果；执行后补充实际结果、版本、时间及缺陷关联。

| 覆盖方面   | 必须检查的内容                                                     | 完成依据                               |
| ---------- | ------------------------------------------------------------------ | -------------------------------------- |
| 业务功能   | 主流程、分支流程、状态变化及业务规则                               | 已确认的验收要求有对应用例和预期结果   |
| 边界与异常 | 空值、边界值、非法输入、重复操作、超时及失败处理                   | 关键异常能够发现，处理结果符合业务约定 |
| 权限与隔离 | 登录状态、角色权限、接口权限及跨用户、跨部门或跨企业的数据访问     | 允许和禁止访问的场景均有验证记录       |
| 关联业务   | 跨页面、跨模块、审批流程、消息通知、定时任务及第三方交互           | 能验证完整业务链路及关键状态一致性     |
| 数据与文件 | 新增修改删除、计算汇总、查询筛选、导入导出、上传下载及历史数据兼容 | 页面、接口、存储结果及关联数据符合预期 |

- 根据场景使用等价类、边界值、场景法和判定表等方法设计用例，并组织产品、研发参与重点用例评审，记录确认结果。
- 用例必须随需求变化和缺陷修复持续更新；将线上问题、重复缺陷和易遗漏场景补入回归用例库。
- 公共能力用例统一维护，项目差异单独标明；失效用例必须更新或归档，避免重复执行无效检查。

### 2.4 测试环境、数据与提测核对

- 接收提测时核对任务清单、自测结果、环境地址、版本或提交号、构建编号、配置和数据库变更，以及已知问题；信息不足时记录原因，由研发补齐。
- 与研发运维核对环境可用性和实际部署版本，准备必要账号及权限；通过冒烟测试快速检查登录、主要页面和核心流程能否运行，再开展详细测试。
- 核心流程不可用或环境异常阻塞测试时，必须记录阻塞范围和时间，分别对接研发或研发运维处理，恢复后重新确认版本及测试条件。
- 准备正常、异常、边界及不同权限的数据，明确来源、用途和清理方式；使用生产数据副本时必须按项目要求脱敏，测试数据和账号必须与正式业务区分。
- 测试数据操作必须限定在授权环境和范围内；涉及共享环境时先协调，避免影响其他人员正在执行的用例。

### 2.5 功能、接口与数据验证

- 按用例验证页面交互、业务规则、状态流转及端到端流程，覆盖需求、优化和 BUG 修复涉及的功能及关联模块。
- 依据[接口文档标准](/backend/other/api-standard)，在 Apifox 中维护对应接口测试用例，检查参数、字段、返回结果、异常处理、身份认证和权限控制，并核对文档与实际行为是否一致。
- 通过接口调用、浏览器开发者工具、抓包、日志和授权范围内的 SQL 查询辅助定位，核对页面、接口及数据库结果；发现问题时保留能够支持复现的证据。
- 对金额、数量、时间、统计汇总、批量操作和导入导出等场景，必须核对计算规则、精度、完整性及关联数据一致性。
- 验证数据库变更对业务、历史数据和新旧版本兼容性的影响；生产数据修正由研发提供并验证 SQL，研发运维按交付脚本执行，测试验证业务结果。

### 2.6 回归与专项测试

- 根据变更说明、缺陷影响和关联关系确定回归范围，覆盖原问题、受影响模块、公共能力及核心业务流程，并保留选取范围的依据。
- 代码合并冲突处理、修复或配置调整引起行为变化时，与研发确认影响范围，补充回归；发布产物变化时重新评估已有验证结论。
- 按项目分工开展性能、兼容性、弱网和安全等专项测试，明确目标、环境、工具、执行范围及评价依据，并记录测试条件和结果。
- 专项测试需要额外环境、资源或专业支持时，提前同步项目负责人协调；不得将未执行的专项测试描述为已经通过。

### 2.7 缺陷管理与跟踪

- 在项目统一的问题入口登记缺陷，关联任务、环境、版本、复现步骤和证据，按业务影响记录严重程度，推动明确修复人员。
- 测试负责说明现象、预期结果和影响，研发负责定位代码及业务逻辑问题，研发运维负责环境问题处理；涉及需求判断时，由产品人员确认业务规则。
- 跟踪缺陷受理、修复交付、复测和关闭，修复后必须验证原问题及受影响内容；验证失败时提供证据并退回修复人员处理。
- 延期、重复、不复现或业务规则争议必须记录处理依据和跟进人员，具体复测及关闭要求按第 3.3 节执行。

### 2.8 基础自动化测试建设

- 将稳定、重复执行频繁的接口和核心业务场景纳入自动化，维护脚本、测试数据、断言及执行说明，输出能够定位失败场景的结果。
- 自动化脚本和配置模板必须纳入版本管理；账号凭据按项目要求管理，不得明文写入源码、普通文档或执行日志。
- 测试负责测试脚本、数据及业务断言维护，研发配合提供可测试接口，研发运维负责执行环境和流水线接入；运行失败时按业务、脚本或环境原因分别处理。
- 自动化暂未覆盖的场景必须保留人工执行安排；脚本通过仅代表其覆盖场景通过，测试结论必须说明实际验证范围。

### 2.9 质量分析、报告与改进

- 按测试批次汇总用例执行、缺陷、复测、回归及遗留风险，明确通过、失败、阻塞和未执行的内容，不得将未测试事项计为通过。
- 输出与实际环境、版本和产物对应的测试报告，按第 3.4 节给出明确结论，为项目负责人确认发布安排提供依据。
- 分析重复缺陷、线上问题和测试遗漏，结合需求、研发自测、环境和用例覆盖情况形成改进任务，明确责任人及完成时间。
- 定期更新核心回归集、测试数据和操作说明，检查改进措施是否有效；质量评价必须结合实际业务影响和证据，不能仅按缺陷数量判断。

### 2.10 上线支持与线上问题验证

- 发布前准备核心业务验证清单，与研发运维、产品及项目负责人明确验证人员、时间、账号使用方式、观察时段和异常反馈渠道。
- 灰度和生产部署后核对版本，按分工执行核心业务验证，及时反馈功能异常、数据错误及权限问题，并提供定位证据。
- 生产验证必须使用约定账号及可控数据，涉及真实业务的操作必须按项目安排执行，产生的数据必须明确保留或清理方式。
- 发现发布异常时立即同步研发运维和项目负责人，配合判断业务影响；回滚或修复后重新验证核心业务，并记录结果。
- 线上问题修复后补充对应回归用例，紧急发布按[研发运维岗职责标准](/responsibilities/devops)第 3.4 节配合执行。

## 三、提测、缺陷与发布分工

以下为本标准的默认分工。每个项目必须明确各角色对应人员；项目负责人按项目分工指定，承担排期协调与发布安排职责。人员兼岗时，必须分别履行对应职责并记录实际执行人员。

### 3.1 角色责任

| 角色         | 负责事项                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 测试人员     | 负责测试计划、用例、数据、执行、缺陷登记与复测、回归、测试结论和发布业务验证，维护测试资产并跟踪质量风险                                          |
| 产品人员     | 负责需求和业务规则确认、验收标准、需求变更说明及客户测试协调，按分工参与业务验收和发布验证                                                        |
| 研发人员     | 负责代码及 SQL 准确性、单元测试与自测、发布内容确认、各环境分支合并和冲突处理，提供提测信息、修复说明及可复测版本；无流水线时交付测试包和构建记录 |
| 研发运维人员 | 负责统一构建环境和流水线、固定生产提交或标签、灰度及生产包构建与核验、各环境部署、环境异常处理、技术检查、监控及回滚                              |
| 项目负责人   | 协调测试与修复优先级、排期和资源，依据测试及验收结论确认发布安排，记录遗留风险的处理决定并跟踪完成                                                |

### 3.2 各环境的测试与发布配合

| 环境     | 测试岗负责事项                                                                             | 阶段完成依据                                                             |
| -------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| 测试环境 | 核对提测版本，执行冒烟、功能、接口、数据及回归测试，登记和复测缺陷                         | 必测范围完成，影响进入下一阶段的问题已处理，形成测试结论及遗留问题清单   |
| 灰度环境 | 验证候选版本和受影响业务，配合产品开展客户上线前测试，核对相较测试版本的差异               | 灰度业务验证及相应流程要求的客户测试通过，确认结果、差异及遗留风险已记录 |
| 生产环境 | 研发运维完成部署及技术检查后，按分工验证核心业务、关键数据和权限，异常时反馈并配合恢复验证 | 核心业务验证及约定观察通过，项目负责人确认发布完成                       |

需求和优化任务分别按[需求流程](/workflow/)及[优化流程](/workflow/optimization)完成客户上线前测试；BUG 任务按[BUG 处理流程](/workflow/bug)执行。客户测试使用的环境和范围按项目安排明确，确认结果由对应客户人员给出，测试记录结果并配合复现及复测。

分支合并、构建、部署和回滚按[研发运维岗职责标准](/responsibilities/devops)执行。研发完成自测并合入测试分支后，由流水线自动部署或研发运维执行部署；无流水线时，研发交付测试包及构建记录，研发运维核验后部署。测试负责提测核对和业务验证。

### 3.3 缺陷复测与关闭

1. **登记与分派。** 测试必须提供环境及版本、前置条件、测试数据、操作步骤、预期与实际结果、复现频率、影响范围和必要证据。涉及敏感数据时按项目要求脱敏，并跟踪明确处理人员。
2. **定位与修复。** 对应研发或研发运维处理问题，实际处理人员交付修复或变更说明、影响范围、验证结果及可复测的版本或环境信息；测试核对部署结果后开展复测。需求争议由产品确认，排期冲突由项目负责人协调。
3. **复测与回归。** 测试验证原问题、相关边界和受影响业务。通过后记录实际版本及证据；失败时退回处理人员；因环境、数据或依赖无法验证时记录阻塞原因，保持待验证状态。
4. **关闭与延期。** 修复类缺陷必须经测试复测通过后关闭；延期未修复问题保留待处理状态，记录风险、责任人、解决时间及项目负责人的处理决定。重复问题关联原记录，不复现或非缺陷问题记录排查、确认依据和处理结论。
5. **经验沉淀。** 对线上、重复和重大问题补充测试场景，按项目安排参加复盘，将用例、数据或自动化改进落实到具体任务。

### 3.4 测试结论与上线交接

| 测试结论   | 判定要求                                                                                                   | 必须记录的事项                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 通过       | 本次必测范围执行通过，影响本次交付的问题已处理并复测通过，符合发布条件且无需附加风险接受条件               | 对应任务、版本、环境、执行结果及确认人员           |
| 有条件通过 | 本次必测范围已执行，核心业务通过，遗留问题未达到项目约定的发布阻断条件，项目负责人已记录风险接受及处理安排 | 问题影响、规避措施、责任人、解决时间和风险接受记录 |
| 不通过     | 存在达到发布阻断条件的问题，或必测范围未完成、实际版本或验证证据无法确认                                   | 阻断原因、影响范围、处理人员及后续验证安排         |

- 测试结论仅适用于已验证的版本和范围；代码、SQL、配置或发布产物变化时，必须评估差异，完成受影响内容的验证后更新结论。
- 测试报告必须包括任务范围、环境和版本、用例执行及回归结果、缺陷及遗留风险、客户确认结果，以及结论、执行人员和时间；不适用事项必须说明。
- 发布前必须交接核心业务验证清单、遗留问题、验证人员及安排，验证结论关联到实际发布包；测试结论及相应流程要求的客户确认结果作为项目负责人确认发布安排的依据。
- 紧急发布的验证范围和流程调整按应急安排执行，必须记录已验证和需补齐内容、风险及确认人员，并在约定时间内补齐验证和记录。

## 四、协作、权限与交接

- **任务归属**：按项目和模块分配测试任务，跨模块或跨项目变更必须明确各方验证范围、执行人员和结果汇总人员，避免遗漏公共能力和关联业务。
- **沟通与升级**：提测退回、测试阻塞、重大缺陷和发布风险必须及时同步对应研发、研发运维及项目负责人；按项目约定时限跟踪，达到升级条件时落实接手人员。
- **需求与排期**：产品确认业务规则和需求变化，研发说明实现影响，测试评估验证工作量，项目负责人协调优先级和交付时间。
- **访问权限**：按任务分配测试平台、账号、日志及数据库查询权限；生产访问和数据操作必须按授权执行，临时支持结束后及时回收权限。
- **资料交接**：项目转交、人员变动或临时支持结束时，必须移交需求与用例、环境与账号使用方式、测试数据、自动化脚本、遗留缺陷及发布安排，明确接收人员。

## 五、工作产出与验收

| 交付内容       | 必须包含的信息                                             | 验收依据                                         |
| -------------- | ---------------------------------------------------------- | ------------------------------------------------ |
| 测试范围与计划 | 关联任务、验收依据、风险、环境、数据、人员、排期及完成条件 | 任务覆盖明确，依赖和时间可落实，变更及阻塞有记录 |
| 测试用例库     | 场景、前置条件、数据、步骤、预期结果、执行记录及缺陷关联   | 覆盖必测范围，其他测试人员能够按用例复现和执行   |
| 测试环境与数据 | 环境地址、版本、账号使用方式、数据范围、准备及清理说明     | 环境及数据满足验证要求，权限和操作范围明确       |
| 接口与专项测试 | 接口用例或脚本、目标、测试条件、工具、执行结果及问题       | 结果可复核，实际覆盖范围及未执行内容清楚         |
| 缺陷与复测记录 | 复现信息、影响、处理人员、修复版本、复测结果及延期依据     | 问题可复现和跟踪，关闭有验证，遗留问题有处理安排 |
| 自动化测试能力 | 脚本、配置模板、数据、断言、执行说明及报告                 | 可以在约定环境重复运行，失败结果能够定位到场景   |
| 测试报告与结论 | 任务与版本、执行和回归情况、客户确认、遗留风险及结论       | 结论有证据，符合本次版本和发布条件               |
| 发布业务验证   | 核心业务清单、实际版本、验证人员、结果及异常处理记录       | 与部署记录对应，业务验证及约定观察结果明确       |
| 质量改进与交接 | 问题分析、改进任务、责任人、完成时间及测试资料             | 改进结果可核验，接手人员能够继续开展测试         |

工作记录必须关联项目任务、缺陷或发布批次；用例、接口测试和流水线平台已有的记录可以直接关联，不得为同一事项重复建立无必要的记录。
