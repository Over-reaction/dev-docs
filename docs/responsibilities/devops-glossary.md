# 研发运维专业术语说明

本文用于辅助阅读[研发运维岗职责标准](/responsibilities/devops)，通过通俗说明和例子解释常用术语。例子用于帮助理解，具体工具、版本和执行要求以项目实际配置及职责标准为准。

## 一、代码、构建与制品

| 术语 | 通俗说明 | 例子 |
| ---- | -------- | ---- |
| 代码仓库 | 集中保存源代码及修改历史的位置 | 在 GitLab 中保存项目代码，查看每次修改 |
| 分支 | 在同一代码仓库中维护不同开发或发布进度的方式 | 测试分支用于集成待测试的代码 |
| 提交号 | 标识某次代码提交的唯一编号 | 根据提交号确定一个发布包来自哪次代码提交 |
| 发布标签（Tag） | 给特定代码提交附加的发布标记，便于定位版本 | 为正式版本创建 `v1.2.0` 标签 |
| 合并申请（MR） | 将一个分支的改动合入另一个分支前，提交合并意图、展示变更并便于协作的申请 | 研发创建将功能分支合入灰度分支的申请，按发布安排完成合并并处理冲突 |
| 构建、打包 | 按项目规则处理源代码和资源，生成可交付文件的过程 | 将 Java 项目编译并打成 JAR 包 |
| 制品、构建产物 | 构建生成并保存下来的交付文件 | JAR 包、前端压缩包、容器镜像 |
| 制品库 | 集中保存和分发构建产物的仓库，也可理解为“构建产物仓库” | 保存多个版本的发布包，部署或回滚时按版本取用；镜像通常存放在镜像仓库 |
| CI/CD | 持续集成与持续交付或持续部署，通过自动化完成代码检查、构建、测试和交付 | 提交代码后自动检查并打包，生产部署按项目规则人工确认后执行 |
| 流水线（Pipeline） | 按规则组织构建、测试、部署等任务的自动化流程 | 自动执行“检查代码、打包、保存产物、部署、健康检查” |
| 构建节点、Runner | 执行流水线任务的计算资源；GitLab Runner 是接收并执行这些任务的程序 | 在配置好 JDK 的服务器上执行 Java 打包任务 |
| 产物校验值 | 按指定算法计算的文件摘要，用于核对文件是否发生变化 | 对发布包计算 SHA-256，核对部署前后的文件是否一致 |

## 二、环境、部署与发布

| 术语 | 通俗说明 | 例子 |
| ---- | -------- | ---- |
| 测试环境 | 用于验证功能、接口和缺陷修复的运行环境 | 测试人员在测试地址验证新增功能 |
| 灰度环境 | 项目约定的上线前验证或小范围运行环境，具体用途和接入范围由项目确定 | 在指定服务器或指定用户范围中验证候选版本 |
| 生产环境 | 向正式用户提供业务服务的运行环境 | 客户日常办理业务使用的系统 |
| 部署 | 将程序包和配置放到目标环境，并启动或更新服务 | 将正式 JAR 包部署到生产服务器并检查启动结果 |
| 发布 | 按计划让指定版本对目标用户生效，并完成相应确认 | 新版本部署验证后，向指定用户开放功能 |
| 灰度发布 | 先让部分用户、请求或服务器使用新版本，观察后再决定是否扩大范围 | 先将少量真实请求交给新版本，确认稳定后逐步扩大 |
| 回滚 | 发布异常时，将程序版本、配置或流量恢复到已知可用的状态 | 新版本启动失败，重新部署上一个可用版本 |
| 发布窗口 | 约定允许执行上线操作的时间段 | 在已确认的晚间时段部署，产品或测试人员同步验证 |
| 健康检查 | 判断程序是否正常运行、关键依赖是否可用的检查 | 启动后检查健康接口及数据库连接是否正常 |

分支用于管理代码，环境用于运行程序；合并分支后，仍需通过构建和部署更新相应环境。单独建立一个名为“灰度”的测试环境，并不自动具备真实流量的灰度发布能力。

## 三、运行、监控与权限

| 术语 | 通俗说明 | 例子 |
| ---- | -------- | ---- |
| 中间件 | 为业务程序提供通信、缓存、注册等通用能力的软件服务 | Redis 提供缓存，Nacos 提供注册和配置管理 |
| 反向代理 | 代替后端服务接收请求，再转发到对应服务的入口 | Nginx 接收网站请求并转发到 Java 服务 |
| 容器 | 在隔离的运行环境中运行程序的方式，通常由镜像创建 | 用 Docker 容器运行应用服务 |
| 镜像 | 用于创建容器的应用、依赖及运行配置等内容的打包结果 | 保存包含指定版本应用的镜像，用于部署 |
| 配置基线 | 已确认并用于核对的环境配置标准或记录 | 记录生产环境使用的端口、服务版本和网络规则 |
| 性能基线 | 系统在已知正常负载下的性能参考值 | 正常业务量下，接口响应时间和服务器资源占用情况 |
| 监控指标 | 用数字反映系统状态的数据 | CPU 使用率、磁盘剩余空间、接口错误率 |
| 告警阈值 | 触发告警的指标边界，通常还要结合持续时间 | 磁盘剩余空间低于项目约定值并持续一段时间后告警 |
| 告警 | 系统发现符合异常条件后，向责任人发出的通知 | 服务停止后发送通知，提醒运维人员处理 |
| 凭据 | 用于证明身份或获取访问权限的信息 | 服务器密码、SSH 私钥、访问令牌 |
| 操作审计 | 记录并核查谁在何时执行了什么操作 | 查询某次生产配置修改的执行人和修改内容 |
| 标准操作规程（SOP） | 将常规操作的前提、步骤、验证和异常处理写成可执行的说明 | 按文档执行服务重启，并验证重启后的运行状态 |

## 四、备份、恢复与稳定性

| 术语 | 通俗说明 | 例子 |
| ---- | -------- | ---- |
| 备份 | 为数据、文件或配置保存独立副本，以便需要时恢复 | 定时将数据库备份保存到约定位置 |
| 数据恢复 | 使用备份或其他恢复机制，将数据还原到指定的可用状态 | 误操作后恢复到经过确认的数据时间点 |
| 容灾 | 为严重故障准备恢复资源、操作步骤和协作安排，使业务能够恢复 | 服务器损坏后，按预案重建环境并恢复数据和服务 |
| 主备、故障切换与回切 | 主备是一种角色分工；主服务异常后切换到备用服务，故障处理后按方案决定是否切回 | 主数据库不可用时切换到备用数据库，条件满足后再按方案处理回切 |
| 集群 | 多个服务实例或节点共同提供服务的部署方式，具体容错能力取决于配置 | 多个应用实例分担请求，故障时由可用实例继续服务 |
| 恢复时间目标（RTO） | 从故障到业务恢复，最多允许中断多长时间 | RTO 为 2 小时，表示目标是业务中断不超过 2 小时 |
| 恢复点目标（RPO） | 按时间衡量最多允许丢失多长时间内的数据 | RPO 为 15 分钟，表示最多允许丢失故障前 15 分钟内的数据 |

版本回滚和数据恢复是不同操作。恢复旧程序版本不会自动撤销已经写入的业务数据；备份任务成功也需要通过恢复验证，才能确认备份可用。
